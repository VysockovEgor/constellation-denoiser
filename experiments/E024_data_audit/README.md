# E024 — Аудит данных, подсчёта сложности и агрегации

**Вопрос.** Можно ли доверять числам E010–E021: нет ли утечки последовательностей между train и test, верен ли сырой BER, правильно ли посчитаны умножения (RM), одинаково ли настраивались семейства, каков шумовой пол и почему агрегатор E021 пропускал точки?

**Правило (до запуска, черновик).** Утечки нет, если для K = 12 доля тестовых окон, найденных в train, ≤ 5 × случайной (1 − exp(−N/16^K)) и < 1 %; иначе `results/gate_status.json` → `halt: true` (очередь стоит), dedup-тест и v4 h119 (1 seed, 60k). Сырой test BER должен совпасть с 0.009551859551859552; RM всех таблиц E010–E023 — с независимыми формулами. Полностью — `config.json` → `rule_draft`.

**Что делает.** `audit_e024.py`: утечка (K = 6, 8, 12, 16, 31; взаимная корреляция меток файлов), таблица файлов (сырой BER, мощность, уровни), бюджет настройки по семействам, шумовой пол (`results/noise_floor.json`, MDD при 5 seeds); `rm_audit.py`: сверка RM (`docs/complexity.md`); `pareto_v2.py`: новый агрегатор — точка = конфигурация с ≥ 3 seeds, семейства из `results/family_map.csv`, уровни ±25 % в лог-шкале, выбор по валидации, все точки и огибающая.

**Было → стало (E021).** Таблица `results/e021_before_after.md` (и `.csv`): v4 w31 (72.37 % при 16 065 RM) теперь лучший на уровне 16 000; DBP Ns8 (592 RM) попадает на уровень 600.

**Команда.** `bash experiments/E024_data_audit/run.sh <стадия>`; стадии: control | main (аудит; dedup только при утечке) | summarize | smoke. Без обучения, минуты на CPU.

**Результаты.** `results/leakage.json`, `leakage_windows.csv`, `leakage_xcorr.csv`, `data_files.csv`, `data_summary.json`, `rm_audit*.csv`, `tuning_budget.csv`, `noise_floor*.{json,csv}`, `pareto_v2_*.csv`; рисунки `figures/E024_*.png`.
